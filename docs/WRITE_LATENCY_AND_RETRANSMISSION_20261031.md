# 配置写入耗时及 TCP 重传核查（2026-10-31）

## 本次状态

已完成本地代码优化及隔离验证。生产服务未替换、未重载、未重启；没有修改路由、防火墙、拥塞控制、MTU 或客户凭据。候选代码仅在服务器独立子进程内验证，文件事务使用自动清理的私有临时目录，未向实际运行核心提交配置。

此次区分两个问题：配置交付慢属于控制面；TCP 重传属于数据传输。减少控制面重复工作可以减少 CPU/IO 竞争，但不能证明线路丢包已经修复。

## 已实现的代码优化

1. `runtime_publication.py`：只保存一个进程内已验证基线的原始配置摘要、socket、核心进程身份、revision 和原生指纹。每次仍调用原生目标预检；只有原始磁盘摘要、socket 和完整运行回执都相符，才省去重复的旧配置预检。缓存为空、进程变更、revision 变更或磁盘变更时恢复完整核验；漂移仍拒绝发布。重启后不盲信磁盘回执填充缓存。
2. 修复 `dict.get(key, expensive_default())` 的默认值提前求值，避免已暂存注册表时仍重复读取和序列化。旧注册表仍读取一次，用于认证名归属核对。
3. `runtime_write_queue.py`：同一批完成状态与加密结果在一个 SQLite FULL 持久事务内提交，全部成功落盘后才释放等待者及队列容量。32 条同批任务的终态提交由 32 次缩减为 1 次；每个请求的入队持久化及文件 WAL 均保留。注入第二条 UPDATE 失败时，整批回滚，等待者不获得成功回执。
4. 减少批后重复查询；未改变同用户跨批顺序、拒绝任务隔离、CAS、fsync、未知结果暂停及历史幂等保留。
5. 新增 `runtime_metrics.py`。受认证保护的 `GET /api/singbox/tasks` 增加 `performance`：各阶段次数、失败次数、最近/平均/最大耗时，以及固定类别的拒绝计数。只保留固定数量统计，不记录异常原文、用户名、连接地址、密码或任务载荷；重启管理进程后统计从零开始。嵌套阶段耗时不可直接相加。

此前 102 条失败只保存了 `MUTATION_REJECTED`，不足以追溯具体业务校验原因。新诊断将重复用户、重复住宅代理、认证名冲突、历史归属冲突、版本冲突、监听就绪拒绝等分开计数；没有放宽这些校验，也没有将失败伪装成成功。

## 重传分段观察

连续三轮被动采样，每轮约 11～12 秒，不测速、不增加业务连接。下表为持续存在于两次采样中的 TCP 连接，其发送方的重传段增量 / 发送段增量。

| 发送方向或组 | 重传段比值 | RTT 中位数 | 说明 |
| --- | --- | --- | --- |
| 深圳发往香港的业务内网 TCP 组 | 0.001%～0.003% | 约 0.26 ms | 此时相对低 |
| 香港发往深圳的业务内网 TCP 组 | 0.624%～0.700% | 约 0.28 ms | 返回方向高于相反方向 |
| 深圳公网入站连接向对端发送 | 0.262%～0.391% | 约 55 ms | 有重传，不能只用全机均值解释每个客户 |
| 香港公网入站连接向对端发送 | 4.843%～6.580% | 约 282～291 ms | 需逐连接定位；可能含直连用户、中转或其他公网连接，不能假定均走深圳 |
| 香港发往住宅代理的 TCP 组 | 0.039%～0.104% | 约 157 ms | 仅表示这个方向，不能证明住宅代理返回香港方向无问题 |

边界：重传段比值不是线路丢包率；短连接及采样中消失的连接不包含在分组增量内。TCP 指标不直接显示 WireGuard 底层 UDP 丢失位置，不能靠此表判定具体交换机、线路商或 MTU 黑洞。

追加 10 秒观察中，深圳/香港的物理网卡及 wg1 接收/发送错误、丢弃、qdisc 丢弃、UDP 缓冲错误、softnet 丢弃均未新增。此前三轮没有 TCP 内存压力、接收队列丢弃或监听队列丢弃新增。两端 wg1 MTU 都为 1420；香港已有 BBR + fq。深圳公网 VLESS 存量连接可见 BBR，其内网连接大多为 cubic，主机默认仍为 cubic。不同方向的拥塞算法不同，尚不能据此认定算法就是丢包原因。

香港 sing-box PID 保持 3866281，管理进程 PID 保持 1469809，均未因本轮验证重启。

## 降低重传的处理顺序

1. 在真实卡顿时段持续保存分段样本，先区分香港公网入站组与内网返回组，按连接/入口对应客户，不用全机重传率替代个体情况。
2. 向线路商提供香港→深圳返回方向的同时段证据，核对方向性 QoS、突发整形、物理端口/虚拟交换机丢弃和隧道底层 UDP。需要线路商计数器才能进一步归因；当前不能断言公网已跑满或内网限速为 500 Mbps。
3. 对香港公网入站高重传的客户/中转分别对照深圳入口，先验证协议身份和线路可达性，再小范围调整；不统一修改域名或切换所有用户。广州线路容量较小，不做平均分流。
4. 若下一阶段证据指向隧道封装或转发器，再做独立测试端口的同出口对照；MTU、拥塞算法、转发路径一次只改变一项。当前未调整这些生产参数。

新增工具 `scripts/diagnose_tcp.py` 只读取 `/proc` 和 `ss`，不发送探测、不修改网络：

```bash
# 深圳入口
python3 scripts/diagnose_tcp.py --role entry --interval 10 --samples 3
# 香港节点
python3 scripts/diagnose_tcp.py --role hk --interval 10 --samples 3
```

原始证据：`optimized-audit-entry.json`、`optimized-audit-hk.json`、`transport-settings-entry.json`、`transport-settings-hk.json`。
